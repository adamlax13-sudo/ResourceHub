# Process Steps Inference Design

**Date:** 2026-02-23
**Status:** Approved

## Overview

Generate realistic process steps for services that are missing steps, have insufficient steps (<3), or have generic/boilerplate steps using Claude AI inference with similar service examples.

## Requirements

1. **Flag inferred steps** - Add `process_steps_inferred` boolean column to distinguish AI-generated steps from scraped ones
2. **Target services with:**
   - Missing steps (NULL, [], 'null')
   - Fewer than 3 steps
   - Generic/boilerplate steps detected via keyword matching + Claude verification
3. **Hybrid inference approach** - Use similar service examples combined with Claude reasoning
4. **Combination detection** - Keyword check first, then Claude verification for borderline cases

## Database Schema

```sql
ALTER TABLE services ADD COLUMN process_steps_inferred BOOLEAN DEFAULT FALSE;
```

- `FALSE` (default) - steps were extracted from actual website content
- `TRUE` - steps were generated by Claude inference

No migration needed for existing data - all current steps remain `FALSE`.

## Two-Phase Architecture

### Phase 1: Detection

**Step 1: Query candidates**
```sql
SELECT * FROM services WHERE is_active = TRUE AND (
  process_steps IS NULL OR
  process_steps::text = '[]' OR
  process_steps::text = 'null' OR
  json_array_length(process_steps) < 3
)
```

**Step 2: Keyword check for generic steps**

Flag services whose steps contain patterns like:
- "Call to inquire" / "Call for more information"
- "Visit website" / "Check website"
- "Contact the organization" / "Reach out"
- "Fill out application" / "Complete form" (without specifics)
- "Attend intake" (with no detail about what intake involves)

**Step 3: Claude verification for borderline cases**

For services that pass keyword check but have <3 steps, ask Claude:
> "Are these process steps specific enough for someone to actually access this service, or are they generic placeholders?"

**Output:** List of service IDs needing inference, with reason (missing/insufficient/generic).

### Phase 2: Generation

**Step 1: Fetch similar service examples**
```sql
SELECT name, category, description, process_steps
FROM services
WHERE category = :target_category
  AND process_steps_inferred = FALSE
  AND json_array_length(process_steps) >= 4
ORDER BY RANDOM()
LIMIT 3
```

**Step 2: Claude inference prompt**
```
You are generating realistic process steps for accessing a social service in Alberta.

CONTEXT:
Service Name: {name}
Category: {category}
Description: {description}
Eligibility: {eligibility}
Location: {location}

EXAMPLES FROM SIMILAR SERVICES:
{formatted_examples}

INSTRUCTIONS:
1. Generate 4-6 specific, actionable steps based on the service type
2. Use patterns from similar services but customize to this specific service
3. Include realistic details (e.g., "Call intake line" → "Call the 24-hour crisis line")
4. Steps should guide someone who has never accessed this type of service
5. Be specific about what happens at each stage (assessment, documentation, etc.)

Do NOT include generic steps like "Visit website" or "Call for info" unless that's truly
the first step with specific details about what to ask/expect.
```

**Step 3: Validation**
- Ensure 3-6 steps returned
- Each step has `action` field with meaningful content
- Flag as `process_steps_inferred = TRUE`

## Script Structure

**New script:** `scraper/infer_process_steps.py`

**Flow:**
```
1. Add column if not exists (idempotent)
2. Query candidate services (missing/insufficient/generic)
3. For each candidate:
   a. Run keyword check → if generic patterns found, flag for inference
   b. If <3 steps and no keywords, run Claude verification
   c. If flagged: fetch similar examples, generate steps, save with inferred=TRUE
4. Print summary report
```

**Error handling:**
- Skip service on Claude API errors (don't halt entire run)
- Rollback individual service on DB errors
- Log reason for each skip/update

**Rate limiting:** 1 second between Claude calls

## Trade-offs Considered

| Approach | Pros | Cons |
|----------|------|------|
| Single-pass | Fewer API calls | Can't distinguish detection from generation |
| **Two-phase (chosen)** | Accurate detection, targeted generation | More API calls for borderline cases |
| Category templates | Very efficient | Less personalized |

Two-phase was chosen for accuracy - keyword check handles obvious cases cheaply, Claude verification catches subtle boilerplate, and hybrid generation with real examples produces realistic steps.
